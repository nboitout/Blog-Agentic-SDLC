The Interception Point

A close read of PreToolUse and PostToolUse — the two hooks that sit on either side of every tool call, one deciding whether it happens, the other deciding what Claude sees afterward.

Pre  gates the call Post  rewrites the result 13 sections
01Position

Where They Sit

Both hooks wrap the same event — a tool call — from opposite sides. Nothing else in the loop gets this vantage point.

02Input shape

One Envelope, Two Moments

Both events receive the same JSON shape on stdin — only hook_event_name tells you which side you're on.

FieldCarries
tool_nameThe tool being called — "Bash", "Edit", an MCP tool name…
tool_inputThe arguments the tool is about to run (or just ran) with
hook_event_name"PreToolUse" or "PostToolUse"
session_id / transcript_path / cwdWhich conversation, its log file, and the working directory
permission_modeThe active mode — default, acceptEdits, plan, bypassPermissions…
tool_use_idUnique id for this specific call, for correlating Pre with Post
agent_id / agent_typePresent only when the call happens inside a subagent
03PreToolUse

The Gate

A PreToolUse hook answers one question — should this call happen, and with what input? — via hookSpecificOutput.permissionDecision.

Add updatedInput alongside allow to rewrite the call's arguments before it runs — e.g. redact a flag, inject a safer default, normalize a path.
04PostToolUse

The Rewrite

The tool already ran — PostToolUse can no longer stop it. It can only shape what Claude reads next.

updatedToolOutput replaces the result for any tool, MCP or built‑in. updatedMCPToolOutput is the deprecated, MCP‑only predecessor. additionalContext appends rather than replaces — use it to annotate without discarding the original.
05Exit codes

The Same Code, Two Meanings

A hook can answer purely through its exit code — but the same code means something different depending on which side of the call it runs on.

Exit codePreToolUsePostToolUse
0Success — JSON on stdout is read, no blockSuccess — JSON on stdout is read
2Blocks the call — stderr becomes the reason Claude seesNot honored — the tool already ran; stderr is informational only
otherNon‑blocking error — call proceedsNon‑blocking error — nothing to stop
If stdout starts with { and ends with }, structured JSON is parsed and takes precedence over the exit code — on PreToolUse, JSON with permissionDecision: "allow" can even override an exit 2.
06Matchers

Scoping a Hook

The matcher string decides which tool calls reach the hook at all — and it's read two different ways depending on what's in it.

exact / list

Plain names

Only letters, digits, _ -, spaces, commas, pipes → matched literally.

"Bash" · "Edit|Write" · "Edit, Write"

regex

Anything else

A paren, bracket, *, ., ^ or $ → the whole string becomes a regex.

"mcp__memory__.*" · "^mcp__" · ".*"

An empty or omitted matcher catches every tool. MCP tools are named mcp__<server>__<tool>, which is exactly why regex matchers exist — to scope a hook to one server's tools at once.
07settings.json

Config Anatomy

Four levels of nesting connect an event to the handlers that run for it.

08Two ways to define one

Config File or Callback

The Agent SDK skips shell scripts entirely — a hook can be a function in your own process.

settings.json
// runs an external command
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{
        "type": "command",
        "command": "prettier --write"
      }]
    }]
  }
}
Agent SDK (Python)
from claude_agent_sdk import HookMatcher

options = ClaudeAgentOptions(
  hooks={
    "PreToolUse": [
      HookMatcher(
        matcher="Bash",
        hooks=[my_guard]  # your fn
      )
    ]
  }
)
09Concurrency

When Hooks Collide

Every hook matching an event fires in parallel, not in the order they're declared.

If more than one hook sets updatedInput on the same call, whichever finishes last wins — the order is non‑deterministic. Treat that as a bug to avoid, not a feature to rely on.
10Boundaries

Security & Limits

What hooks can enforce — and what they can't get around.

runs as you

Full user permissions

A hook script has your filesystem access and credentials — it validates its own input, nothing sandboxes it for you.

deny always wins

Even in bypassPermissions

A PreToolUse deny blocks the call in every permission mode. allow can't override a settings‑level deny rule.

can't undo

PostToolUse is too late

By the time it runs, side effects already happened — it can only shape what Claude reads about them.

10 min default

Timeouts are generous

Command, HTTP and MCP‑tool hooks default to a 600s timeout — override per handler if a check should fail fast.

11In the wild

Four Patterns

Most real hooks are one of these, wearing different clothes.

PreToolUse

Secrets gate

Scan tool_input for a Bash command touching .env or a key pattern → deny with a reason.

PostToolUse

Auto‑format

Matcher Edit|Write runs prettier or black on the touched file right after the edit lands.

PostToolUse

Output normalization

One hook sets updatedToolOutput for every tool family so downstream logic never branches on MCP vs. built‑in.

PostToolUse

Audit trail

Every Bash call gets appended to a log via additionalContext or a side file — a record Claude never has to ask for.

12The model

Two Questions, One Boundary

Before the call, you're guarding the gate. After the call, you're shaping the memory. Everything in this deck is one of those two jobs.
