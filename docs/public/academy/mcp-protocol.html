One Protocol, Any Tool

A close read of the Model Context Protocol — how a Host, a Client, and a Server agree on what an LLM is allowed to touch, and the wire format underneath every MCP server you've ever connected.

01Why it exists

The M×N Problem

Before MCP, every AI application needed a bespoke integration for every data source. M apps × N tools meant M×N integrations — each one rebuilt from scratch.

Anthropic's own framing: MCP is to AI context what the Language Server Protocol is to code editors — one interface, any editor, any language server, no N×M rewrite.
02Architecture

Host, Client, Server

Three roles, not two. The Host is the application you're using; it creates one Client per connection, and each Client speaks 1:1 to exactly one Server.

One Client per Server is a hard rule, not a convention — it's what keeps a compromised or misbehaving server from reading traffic meant for another.
03Transports

Two Ways to Connect

The primitives above are transport-agnostic — the same tools/call works whether the server is a subprocess or a website.

stdio

Local subprocess

The client spawns the server and talks over its stdin/stdout. No network, no auth handshake — the process boundary is the security boundary.

Streamable HTTP

Remote server

A single HTTP endpoint accepts POSTs and can stream responses back over SSE. Supports auth, multiple concurrent clients, resumable sessions.

The original two-endpoint HTTP+SSE transport (separate /sse and /messages endpoints) was superseded by Streamable HTTP in the 2025-03-26 spec revision — if you see it in older docs, it's the predecessor, not an alternative.
04Wire format

Underneath: JSON-RPC 2.0

Every MCP message is one of three JSON-RPC shapes — the transport changes, this doesn't.

request — expects a response
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": { ... }
}
notification — no response expected
{
  "jsonrpc": "2.0",
  "method": "notifications/tools/list_changed"
}
// no "id" field at all
A response carries the same id as its request, and either a result or an error — never both. Requests can flow in either direction: the server can call back into the client too.
05Lifecycle — stable baseline

Initialize, Then Go

The handshake every MCP implementation you'll meet today still runs: negotiate a protocol version and capabilities, then confirm you're ready.

Both sides **MUST** hold off on non-ping requests until this completes — the client waits for the response, the server waits for initialized. This is the 2025-06-18 spec's lifecycle, and it's what essentially every deployed server implements right now.
06Lifecycle — the 2026-07-28 rewrite

Going Stateless

The most recent spec revision removes the handshake entirely — worth knowing about, still landing across the ecosystem.

2025-06-18 · stable

Session-based

One initialize handshake opens a session; an Mcp-Session-Id ties every later request back to it.

2026-07-28 · latest

Stateless

No handshake, no session id. Every request carries its own protocol version and capabilities in _meta; an optional server/discover call learns capabilities upfront.

The stated payoff: "any request can now land on any server instance behind a plain round-robin load balancer without needing shared storage." This deck flags it as the newest layer, not the one to assume is deployed everywhere — check which spec version a given server actually targets.
07Vocabulary

Six Primitives, Two Directions

Three things a server offers a client; three things a client can offer back to a server.

server → client

Tools

Model-controlled actions the LLM can invoke — tools/list, tools/call.

server → client

Resources

App-controlled readable data — files, records — addressed by URI.

server → client

Prompts

User-controlled reusable templates the host can surface as slash commands.

client → server

Sampling

Lets a server ask the client's LLM to complete something, without seeing raw model access itself.

client → server

Roots

The client tells a server which filesystem boundaries it's allowed to operate within.

client → server

Elicitation

A server can ask the client to collect a specific piece of missing input from the user mid-task.

08Deprecation watch

Sampling, Roots & Logging: Deprecated

Accepted proposal SEP-2577 deprecates all three — low adoption relative to their implementation cost was the stated reason.

WhatWhy deprecated
RootsVague semantics, overlapping with tool parameters and server-side config
SamplingComplex to implement correctly; adoption stayed low
LoggingRedundant with stderr and OpenTelemetry-based alternatives
It's advisory only — no wire-level break. Deprecated features keep working for at least 12 months from the deprecating spec version. What's replacing the server-to-client interaction pattern they enabled: Multi Round-Trip Requests (MRTR), where a stateless call can return resultType: "input_required" and get retried with inputResponses.
09Discovery

Listing & Change Notifications

A client doesn't hardcode what a server offers — it asks, and can be told when the answer changes.

The same shape repeats for resources/list and prompts/list — each gated behind its own listChanged capability flag from initialization.
10Trust signals

Tool Annotations: Hints, Not Guarantees

Stable since the 2025-03-26 revision — four booleans a tool definition can carry to describe its own behavior.

readOnlyHint

Doesn't modify state

Safe-looking calls a client might auto-approve more readily.

destructiveHint

May cause real damage

Deletion, overwrites — the kind of call worth a confirmation.

idempotentHint

Safe to repeat

Calling it twice with the same input has no extra effect.

openWorldHint

Touches the outside world

Web search, external APIs — results a client can't fully predict.

The spec is explicit: annotations are self-reported and untrusted by default. "A server can claim readOnlyHint: true and delete your files anyway." Clients MUST treat them as untrusted unless the server itself is trusted — real safety comes from sandboxing and access control, not from reading these hints.
11Remote servers

Authorization: OAuth 2.1

Only relevant over HTTP — a local stdio server just inherits credentials from its environment.

Dynamic Client Registration (RFC 7591) lets a client register with a server it's never seen before, no manual setup. PKCE is mandatory — not optional hardening. The resource parameter binds a token to one specific server, which is exactly what stops a stolen token for Server A from working against Server B.
12The model

Client Asks, Server Answers

Everything else — transports, JSON-RPC, the handshake, annotations, OAuth — exists to answer one question honestly: what can this client see, and what will this server actually do. Every MCP server your Agent SDK Host connects to is this same shape.
