You Decide, Claude Code Enforces

A close read of the permission system — modes, rules, sandboxing, and the settings that govern them — and why none of it depends on the model behaving.

You  grant, deny, or set the mode Claude Code  enforces it, every call 13 sections
01The core question

Not the Model's Decision

Every tool call asks one question — allow, ask, or deny — and the answer is decided by Claude Code, not by anything in your prompt or CLAUDE.md.

"Permission rules are enforced by Claude Code, not by the model." Instructions in a prompt or CLAUDE.md shape what Claude attempts — only /permissions rules, a permission mode, or a PreToolUse hook actually grant or revoke access.
02Baseline

Six Modes, One Risk Ladder

A permission mode sets the baseline for every session. Rules and hooks layer on top of whichever one is active.

ModeRuns without askingBest for
default (Manual)Reads onlySensitive work, reviewing every action
acceptEditsReads, file edits, common filesystem commandsIterating on code you're reviewing
planReads, classifier-approved commands where availableExploring before you change anything
autoEverything, with background safety checksLong tasks, fewer prompts
dontAskOnly pre-approved tools — denies instead of askingLocked-down CI and scripts
bypassPermissionsEverythingIsolated containers and VMs, nothing else
Writes to protected paths are never auto-approved in any mode except bypassPermissions. Deny rules block in every single mode — that one is genuinely never negotiable.
03auto mode

A Second Model Reviews Instead of You

In auto mode, a separate classifier model evaluates each action against your request — it isn't the same model doing the work and grading itself.

blocks by default

High-consequence actions

Piping to a shell (curl | bash), production deploys, mass deletions, IAM changes, terraform destroy, force pushes.

allows by default

In-scope work

Edits inside the working directory, dependency installs from a lock file, read-only HTTP, pushes to the branch you started on.

On Pro, Max, and Team plans, auto is the built-in starting mode. It requires a supported model, and an organization can remove it entirely with permissions.disableAutoMode: "disable". rm/rmdir against a critical path still routes to the classifier, never a silent auto-approve.
04Fine-grained control

Tool or Tool(specifier)

The same shape reappears everywhere — a bare tool name for everything, parentheses to narrow it.

RuleMatches
Bash(npm run *)npm run build, npm run test --watch — not npm install
Read(./.env)Exactly that file, this directory
WebFetch(domain:*.example.com)Any subdomain of example.com
mcp__github__get_*Every get_ tool from the github MCP server
Agent(model:opus)Subagent calls that request the Opus tier
Claude Code is shell-aware: Bash(safe-cmd *) does not grant safe-cmd && rm -rf / — each subcommand around && || ; | is matched independently. You can't gate on a tool's primary content field (command, file_path, url) with a parameter rule — that's exactly the kind of rule a compound command would bypass.
05Evaluation order

Deny, Then Ask, Then Allow

Fixed order, not configurable, and specificity never changes it. First match in that order wins.

A broad deny rule can't carry allowlist exceptions — a narrower allow for the same call simply never gets evaluated. A bare tool-name deny (Bash, not Bash(rm *)) removes the tool from Claude's context entirely; it never even sees the option.
06Where rules live

Five Files, One Precedence

Highest wins for a single value; array-type keys like permissions.allow merge across every level instead.

1 · highest

Managed settings

MDM, org console. Locks a rule so nothing below can override it.

2

Command line

claude --settings, for one run.

3

Project local

.claude/settings.local.json — personal, gitignored.

4

Shared project

.claude/settings.json — checked in, whole team.

Level 5, lowest: ~/.claude/settings.json, user-wide. "Yes, and don't ask again" on a Bash command or WebFetch domain saves permanently to project-local settings at the repository root — resolved through worktrees, so the rule reaches every checkout of that repo.
07The risky one

Everything, Except a Short List

bypassPermissions skips prompts entirely — but "entirely" has real exceptions, in every mode including this one.

never auto-approved, anywhere

Five standing exceptions

Explicit ask rules · rm/rmdir on a critical path · AskUserQuestion and MCP tools requiring interaction · org connector tools set to ask · cross-session messaging safeguards.

the warning is not boilerplate

Isolated environments only

A prompt-injection attack or a model error can cause destructive action with nobody in the loop. Writes to .git and .claude ARE skipped here — that's real exposure outside a sealed container.

An organization removes it entirely with permissions.disableBypassPermissionsMode: "disable" in managed settings — the setting that actually matters for a governed deployment, since it can't be overridden downstream.
08A different layer

What Runs vs. What It Can Reach

Permission modes decide whether a call happens. The Bash sandbox — Seatbelt on macOS, bubblewrap on Linux/WSL2 — decides what it can touch once it does. The two are independent.

filesystem, by default

Working directory only

Writes stay inside the working directory, the session temp dir, and anything added via --add-dir. Everything else: denied automatically.

network, by default

No domains at all

First request to a new domain prompts — or in auto mode, goes to the classifier. Nothing is reachable until it's explicitly allowed.

Auto-allow mode runs sandboxed commands without asking at all — but deny rules, critical-path rm/rmdir, and content-scoped ask rules like Bash(git push *) still apply even then. A command the sandbox can't run falls back to the regular permission flow, visibly labeled "Bash command (unsandboxed)."

It exists for exceptions the static rule list can't express — rules and modes handle the common cases first. For logic that must run on every call regardless of mode, a PreToolUse hook is the right tool, not this callback.
10Two kinds of "no"

Protected Paths vs. Critical Paths

They sound similar and behave differently — one has an escape hatch, the other doesn't.

 ExamplesBypassed by bypassPermissions?
Protected paths.git, .claude, .mcp.json, shell rc filesYes — genuinely skipped there
Critical pathsFilesystem root, /home, working-directory parentsNo — rm/rmdir here always prompts
Critical-path removal is the one guardrail no allow rule and no PreToolUse hook "allow" decision can approve away. It's the actual floor beneath every mode, bypass included.
11For an organization

Locking It Down at the Org Level

Managed settings are the only layer nothing downstream can override — the actual governance surface.

disable a mode

permissions.disableBypassPermissionsMode

Removes bypass from the mode cycle for everyone, everywhere.

disable auto

permissions.disableAutoMode

Forces classifier-free, manual review as the ceiling.

force sandboxing

sandbox.enabled + failIfUnavailable

Makes the sandbox a hard requirement, not a best-effort fallback.

lock rule sources

allowManagedPermissionRulesOnly

Ignores project- and user-level rules entirely — only managed settings decide.

12The model

Layers, Not a Single Gate

No single layer is the whole story. Rules and modes decide whether Claude Code even tries, and the sandbox and hooks bound what happens either way — the same PreToolUse hook from the very first deck in this series is still standing at that same gate.
