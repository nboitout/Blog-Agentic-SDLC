01Why it exists

The CLAUDE.md Problem

Everything in CLAUDE.md loads on every single turn, whether it's relevant or not. A skill only loads when it's actually needed.

Create a skill exactly when you catch yourself pasting the same instructions into chat again, or when a CLAUDE.md section has grown from a fact into a procedure.
02Anatomy

One Folder, One Required File

A skill is a directory. SKILL.md is the only file it needs — frontmatter on top, instructions below, extra files alongside.

my-skill/
my-skill/
├── SKILL.md        # required — overview + nav
├── reference.md    # loaded only if linked-to
├── examples.md      # loaded only if linked-to
└── scripts/
    └── helper.py   # executed, never loaded raw
SKILL.md
---
name: commit
description: Stage and commit changes.
  Use when the user asks to commit.
allowed-tools: Bash(git add *)
---

# instructions, third person,
# under 500 lines
1. Review the diff
2. Stage relevant files
3. Write a commit message
All frontmatter fields are optional — only description is recommended, so Claude knows when to reach for it. Without one, Claude falls back to the first markdown paragraph.
03The core mechanic

Three Levels of Loading

This is the whole point of a skill: content arrives in layers, and each layer only loads when the one before it justified it.

LevelWhenCostContent
1 · MetadataAlways, at startup~100 tokensname + description from frontmatter
2 · InstructionsWhen the skill is triggeredunder 5,000 tokensThe rendered SKILL.md body
3 · ResourcesAs needed, if Claude follows a linkzero until accessedreference.md, examples.md, scripts — scripts return only their output
"Progressive disclosure ensures only relevant content occupies the context window at any given time." Every other frontmatter field just fine-tunes when Level 2 fires and who's allowed to trigger it.
04The matching signal

What Claude Actually Reads

At startup, Claude sees every skill's description and nothing else. That's the entire basis for deciding whether to invoke one.

weak

"Handles PDFs"

Says what, not when. Claude has no signal for which requests should trigger it.

strong

"Extract text and tables from PDFs, fill forms, merge documents. Use when working with PDFs or the user mentions PDF extraction."

Key use case first, then explicit trigger language — both the what and the when.

The combined description + when_to_use text is truncated at 1,536 characters in the skill listing — front-load the part that actually distinguishes this skill from the others in context.
05Invocation

Two Ways In, One Load

By default both paths are open at once — you can always type the name, and Claude can always decide the description matches.

Arguments follow whichever path fires: $ARGUMENTS, positional $0/$1, or a named $issue declared via the arguments frontmatter list. You can even stack up to six skills in one line — /write-tests /fix-issue 123 — and the trailing text becomes $ARGUMENTS for each.
06Gating a skill

Not Every Skill Wants Both Doors Open

Two booleans narrow the default "either of us can trigger this" down to exactly one side.

FrontmatterYou invokeClaude invokesUse it for
(default)yesyesMost skills — let either side reach for it
disable-model-invocation: trueyesnoSide-effecting actions — /deploy, /commit. You decide the timing, not "the code looks ready."
user-invocable: falsenoyesBackground knowledge with nothing for a person to run — legacy-system-context
If Claude tries to run a disable-model-invocation skill anyway, Claude Code blocks the call outright and tells Claude not to reproduce the steps another way — expect it to suggest you run the command yourself instead.
07Scoping

Where Skills Live

Four locations, each answering "who can use this" differently — and a clear order when two of them define the same name.

enterprise

Managed settings

Every user in the org. Overrides everything else with the same name.

personal

~/.claude/skills/

All of your projects. Overrides a project skill of the same name.

project

.claude/skills/

This project only — also every parent directory up to the repo root.

plugin

plugin/skills/

Namespaced plugin:skill — never conflicts, loads alongside.

A skill also beats a same-named .claude/commands/ file, and any local skill beats one synced from your claude.ai account. Nested apps/web/.claude/skills/ skills load only once Claude touches a file in that subdirectory, and surface under a directory-qualified name if they clash with the root.
08Permissions

A Grant for This Turn, Not This Session

allowed-tools and disallowed-tools both apply only for the turn that invokes the skill — then they clear.

allowed-tools — pre-approve
---
name: commit
disable-model-invocation: true
allowed-tools: Bash(git add *)
  Bash(git commit *)
---
disallowed-tools — remove
---
name: background-loop
disallowed-tools: AskUserQuestion
---
# keeps an autonomous skill from
# ever stopping to ask a person
Neither field is a security boundary against Claude — every tool stays technically callable, and your session's own permission settings still govern anything not listed. allowed-tools just skips the approval prompt. And it isn't gated by workspace trust: a project skill's grant applies even in a folder you've never trusted — review a repo's checked-in skills before you run Claude Code there.
09Lifecycle

Loaded Once, Kept Around

Once a skill's body enters the conversation, it stays — Claude Code never re-reads the file on later turns.

Re-attached skills share a combined 25,000-token budget, filled most-recent-first. Only the skill's instructions persist this way — an allowed-tools grant clears the moment you send your next message, every time, compaction or not. If a skill seems to stop influencing behavior, it's usually still loaded and Claude is just choosing something else — re-invoke it, sharpen the description, or fall back to a hook for anything that must be deterministic.
10Dynamic injection

Grounding a Skill in Live Data

A line starting with ! runs before Claude ever sees the skill — its output replaces the placeholder, the command itself never does.

SKILL.md
---
description: Summarize uncommitted
  changes and flag risks.
---

## Current changes
!`git diff HEAD`

## Instructions
Summarize in 2-3 bullets, then
list risks …
what Claude receives
# the actual diff text,
# already inlined —
# not the git command

diff --git a/app.py b/app.py
+  def validate(x):
+      return x is not None
…
A non-zero exit aborts the whole invocation — Claude never sees the skill content that turn. One carveout: exit code 1 from search/comparison commands like grep counts as a normal result. Each command runs under a 2-minute timeout, and never prompts for permission — a rule that would normally ask instead aborts the call. This never runs at all for a skill synced from your claude.ai account.
11context: fork

When a Skill Needs Its Own Room

Add context: fork and the skill's body becomes a subagent's entire task — no access to your conversation history at all.

Only makes sense for skills with an actual task, not reference guidance — a fork given "use these API conventions" gets no actionable prompt and returns nothing useful. Its edits also land outside your session's checkpoints, so /rewind can't undo them — that's a job for git. Explore and Plan agents skip CLAUDE.md entirely to keep the fork's context small.
12The model

Described Cheaply, Loaded Precisely

A skill is just a bet that most turns won't need it — so it stays a description until one does, and only then becomes instructions Claude actually reads. Everything in this deck — frontmatter, scoping, forking — exists to make that bet cheap to place and easy to control.
